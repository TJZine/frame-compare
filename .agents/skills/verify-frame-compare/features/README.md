# Frame Compare feature map

Choose a user goal, read its feature file, and follow the parent skill's
[Launch, Doctor, Evidence and Cleanup](../SKILL.md) around the drive. This is the
maintained application-verification map; the dated
[pilot](../../../../docs/plans/2026-10-15-verification-map-pilot.md) remains historical
evidence, not a source of current pass claims. The initial three features do not
cover all Frame Compare behavior.

| User goal | Driver and observable result | Explicit boundary |
| --- | --- | --- |
| [Plan a comparison; consume typed JSON failure](cli-planning.md) | Installed CLI subprocess; JSON, exit status and unchanged workspace | Empty media proves planning, not decoding or fresh-package installation |
| [Open an offline report and review frames](offline-report.md) | Production-generated report in headless Chrome; loaded images, controls and note input | Synthetic images; full export/import after moving machines remains unobserved |
| [Confirm alignment and resume the comparison](alignment-review.md) | Actual VSView user route documented; existing Qt/authority tests provide narrower supporting proof | Full native review requires a decoder/desktop; no native or Windows pass follows from offscreen tests |

Creation baseline: the preceding pilot observed installed CLI, Chrome and offscreen
Qt selections on macOS. Its receipts do not establish a new run at the current
checkout. This skill's creation must itself be proved through at least one mapped
real drive, with surviving evidence, before it is called validated. No physical
Windows execution or full native-media review has been established by this map.

On maintenance, reconcile this index with its sibling feature files, source and
current user entrypoints. Account for unreachable native/Windows prerequisites
explicitly; a partial run cannot be reported as a clean full-map live pass. Do not
add a feature solely because an internal module exists: identify a concrete user
route and its observable outcome first.
